## Owner decisions

The owner selected Google as the login provider. For developer startup from IntelliJ with supporting services running locally, sign-in is controlled by an application YAML boolean. It defaults to **off in `dev`** and **on in `prod`**. These are overridable defaults, not a rule forbidding explicit disablement in production. This supersedes the earlier hard development-only restriction in commit `4f9a737` and the separate local-product interpretation in `da08ee3`.

Use `app.auth.enabled` as the planned property name. The common default is true; `application-dev.yml` sets false and `application-prod.yml` sets true. In development with the value false, the server automatically uses a persistent development administrator account from the database, without Google login/configuration. Existing ownership predicates and quotas still apply. When true, Google sign-in is required; missing Google configuration must not silently change the boolean. The owner selected database-backed development-admin provisioning/automatic sign-in; exact fixture identifiers, schema and property binding remain T3 design work. This is the accepted planned configuration, not an implemented setting yet.

Google is the sole application login provider; no separate password-based admin login is selected. The initial plans had no application-admin capability. The owner now requests session controls for users and administrators: administrators can revoke a selected user session or all of that user's sessions. Administrators must also be able to assign/revoke individual permissions in the app. The owner selected a one-time internal setup command for the first permission manager; the exact permission catalog and admin UI design remain open; private-content access is not implied.

The owner requested Google research and an audit of plans, files and current issues before continuing brainstorming. This authorizes the research and planning reconciliation, not feature implementation or completion of issue #3. [The roadmap](../../roadmap.md) owns task authority; [the application design](../application.md) owns amended R1/R18 and C7.

On the first successful Google sign-in, create the application account automatically and let the user start creating projects immediately. No separate registration form, profile-completion step, invitation or approval is required. Returning sign-ins resolve the existing account; concurrent first sign-ins must not create duplicate accounts.

Session defaults are **30 minutes of inactivity** and **8 hours maximum from sign-in**, both configurable in YAML and enforced by the server. A valid session survives closing/reopening the browser and backend restarts within both limits; restarts do not reset its age. Expiry preserves the current view and unsent question while requesting sign-in again. Restore private view/draft state only for the same application account; these UI obligations apply as their owning features are introduced.

Each signed-in session has its own inactivity countdown and maximum lifetime; activity on another device does not extend it. Users can view/manage their sessions from settings or profile and revoke an individual session or all sessions. Ordinary sign-out affects the current session; the explicit all-sessions action includes the current session. Expiry happens independently per session. Administrator revocation must use an explicit permission and take effect across web instances; it does not grant access to the user's private documents/chats. Device/session representation, safe display metadata and concurrent-request revocation behavior need bounded design.

The owner requires an explicit permission system; a role-only authorization model is insufficient. Backend actions must check the needed permission together with resource ownership. Google establishes identity; application permissions and their assignments are managed by this application. Administrators assign/revoke individual user permissions through the app, and new accounts receive basic permissions automatically. Optional role grouping is not a substitute for those controls. The basic set includes ordinary own-project/document/chat/session actions and full-project share/import by default; exact permission identifiers/granularity need design. Disabling sign-in does not disable permission checks: the server-established no-sign-in account uses the same authorization paths. Permission identifiers/default representation, setup-command implementation, exact UI and cross-instance propagation need the bounded design; no general policy language is selected. The 2026-11-07 amendment below selects per-account grants without inherited template membership or a permanent deny state. A deliberate all-user grant may restore an individually removed permission.

## Accepted basic permission set

The owner accepted ordinary own-project/document/chat/session capabilities and now explicitly selected full-project sharing/import as basic permissions, individually revocable by an administrator. Administrative accounts receive the same basic capabilities plus their additional administrative grants and can use the ordinary website through the same account. Ownership, explicit recipient authorization and existing quotas still apply; administrative status alone grants no access to other accounts' private originals. Individual grants/revocations remain authoritative for administrators as well, with the accepted last-permission-manager safeguard. The table is the selected capability scope; exact permission IDs/granularity and feature migrations remain bounded-design/owning-slice work, not an implementation allowlist.

| Area | Basic ordinary-user actions | Existing scope |
| --- | --- | --- |
| Projects | Create, list/open, rename and delete owned projects | T4/T11; preserve confirmation and tracked purge |
| PDFs | Upload, open originals/citations, archive/unarchive, view processing status and retry eligible failed work | T6/T18/T20/T7; no PDF editing or individual PDF deletion |
| Chats | Create/reopen/read, ask questions/follow-ups, delete owned chats and change eligible source selections | T8/T9/T20; keep document ownership and archive rules |
| Own sessions | List and revoke individual sessions or all own sessions | T3; independent idle/absolute expiry |
| AI/operation status | See the account's AI availability/limits and its own operation status | T5 and producing slices; permission never bypasses spending/quota admission |
| Share own project copies | Basic by default: create/revoke fixed copies for intended recipients or registered-link acceptance | T16/T19; explicit share action and existing independent-copy rules |
| Import an authorized project copy | Basic by default: accept/import subject to account/storage quotas | T16/T19; permission alone grants no access to an unshared source |
| Standalone chat sharing/snapshots | Dropped entirely, restricted and public alike | R27/T17 withdrawn; no publication permission, route or admin override |

Administrative session revocation and permission assignment/revocation are separate from the basic set. No default permission grants access to another account's private resources. Permission checks remain combined with resource ownership; resource IDs and browser-supplied permission lists do not authorize access. The exact permission matrix must be tested on the backend, consistent with [OWASP authorization guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#enforce-least-privileges) (checked 2026-11-05).

The owner accepted project-share/import as basic defaults, subject to individual administrator revocation. Administrators receive these same basic permissions plus administrative capabilities; they use the ordinary project/PDF/chat workflows without a second user account. Sharing is limited to complete project copies and importing those copies. Standalone chat sharing and all chat snapshots are dropped. The owner clarified that everything is copied, including all saved chats/messages/citations and source settings. T19 is required within the same import pipeline; no include-chats selector or files-only mode exists. The owner explicitly rejected public/anonymous chat publishing, including an administrator-granted exception: no such permission or public-view route is supported. This supersedes the earlier proposal in `2996c7e` and amends R27/T17. No anonymous account/login workflow is introduced. This earlier public-only removal is superseded by withdrawal of all standalone chat sharing. Project imports remain independent in both directions: edits/deletions in either project never change the other. Share revocation stops future imports without erasing accepted copies. Every project-share/import action remains explicit.

Alternative rejected by the owner: public snapshots enabled through an extra administrator-granted permission. The owner removed anonymous/public viewing entirely. Public URLs would not technically require anonymous accounts; this exclusion is a product decision, separate from Spring's anonymous security-context support. [Spring anonymous authentication](https://docs.spring.io/spring-security/reference/servlet/authentication/anonymous.html) Keep ordinary public login/static/health endpoints and the configured developer no-sign-in principal separate from that product decision; the development principal still satisfies ownership/recipient checks. Definitions of `read`/`write` do not add PDF editing, individual file deletion or unlimited AI use.

## Accepted project-sharing access modes

**Owner confirmation, 2026-11-06:** the owner of a project chooses either a specific-recipient invitation or a general sharing link. A recipient-specific invitation permits only the designated signed-in application account to import. A general link permits any signed-in account possessing it and currently holding import permission, subject to the existing quotas and lifecycle checks. Forwarding a general link can therefore permit another eligible account to import an independent full copy. No anonymous access or standalone chat sharing is added.

Stable recipient binding and exact selection/acceptance UI belong to T16's bounded design; T3 supplies trusted account identity and current permission checks. Full-project capture/history mapping remains T16/T19 work. This confirmation does not authorize those implementations.

## Basic-permission evolution

**Owner-selected model, 2026-11-07:** persist individual permission grants. Basic/Admin are convenient permission templates, not stored memberships on accounts. A user holds actual grants; removing a grant removes access. Do not create a permanent explicit-revocation/deny state for enforcement.

The owner clarified that a deliberate decision to grant P to all users includes Ben even if an administrator previously removed P from Ben. This expressly supersedes the earlier blanket requirement that newly basic/global updates never restore individual removals, and supersedes the shared-default/exception recommendation and its permanent-deny variant. The owner accepted targeting accounts directly rather than interpreting any saved template assignment.

New accounts receive the current basic grants automatically. A reviewed rollout of new basic permissions populates grants for existing accounts too, without session refresh or Google sign-in. An intentional all-user grant may also add an existing permission previously removed from an account. Do not silently reapply templates on ordinary login/restart, replay initial-admin grants or make every template edit synchronize accounts. Removing a grant remains effective until another deliberate grant operation includes that account.

Current authorization reads stored grants, together with ownership, recipient, lifecycle, quota and spending rules. No live Basic/Admin membership or browser permission list confers authority. Optional administrative audit capture and retention remain unchanged; audit history is not current authorization or permanent revocation state.

Applying a template creates actual grants. On 2026-11-07 the owner selected additive application: add the template's listed permissions, preserve all other grants and let admins remove individual permissions separately. Reapplying an already-held grant does not duplicate it. Do not replace the user's grant list or persist a template assignment. Exact template IDs, UI and authorized application/rollout interfaces remain design work; this does not introduce an editable role hierarchy or runtime template-management subsystem.

Grant rollout completion/progress, concurrent account creation and permission edits, retries, stable permission identifiers, splits/replacements and cross-instance visibility still require a concrete transaction/schema design. Ordinary automatic recovery must not silently replay a completed rollout over a later removal. A deliberate new global grant may do so. No implementation or load evidence exists yet.

Preserve the last-permission-manager invariant and atomic order between permission changes and operation admission. Already-admitted work retains its original accepted scope. Initial normal/development grants are still created once and are not restored merely by restart or sign-in. The [Technical Plan](design_draft.md#2-permission-storage--selected-per-account-grants) records the selected model and remaining application choice.

## Accepted initial administrator setup

The owner accepted a one-time operator-run setup command that grants the initial permission-management, administrator session-management and audit-inspection permissions to an explicitly selected existing application account UUID. This replaces manual initial assignment as the selected setup workflow; the command is planned, not implemented.

1. The operator signs in through Google normally, creating an ordinary account with basic permissions.
2. From the trusted application host/environment, the operator invokes the internal setup command with that account UUID. Exact command syntax is a design output; no such command exists yet.
3. The application verifies the account, grants the defined initial permissions transactionally, and records the bootstrap completion and grant evidence without tokens/private content. First successful bootstrap consumes the setup facility; concurrent/duplicate attempts cannot grant a different account.
4. Subsequent assignments/revocations happen in the permission-management UI under the accepted permissions. Ordinary startup must never replay the initial grant or undo a later revocation.

This is an operator action rather than a public setup endpoint. Normal users cannot invoke it through the application UI/API, and being the first registrant must not confer administrator permissions. Do not create a separate local-password admin account or trust a matching email string as proof of identity. The concrete trusted-host invocation, transaction/concurrency rules and failure recovery need bounded design. Removing the last permission manager is forbidden. A later external-account-loss recovery procedure is a separate unresolved question; it must not be an always-on bootstrap backdoor.

This recommendation replaces neither the owner's Google login decision nor in-app permission management. It is the selected way to establish the first permission manager without requiring ad hoc SQL edits, automatic privilege assignment on every startup or a generic role-only seed.

After initial setup, the application must retain at least one account with permission-management access. Reject a permission change that would remove the last such account, including self-revocation and concurrent changes by multiple managers. Enforce this against shared database state atomically; UI disabling alone is insufficient. Count account permissions, not currently signed-in sessions, so ordinary logout/expiry remains valid. Any future account-disabling/deletion operation must preserve the invariant when introduced; this does not add those features now. External Google account loss and operator recovery remain a separate design/operations concern.

New requests still require a valid session; permission/resource/admin revocation is separate. Planned timing properties (not implemented yet):

The owner accepted the [permission-revocation boundary](concepts_brief.md#other-review-findings): check current permissions/ownership on each new protected request, while preserving already-authorized requests and specific durably accepted queued/running operations within their original bounds. Order acceptance against revocation atomically. Result/status/file reads and new user-triggered retries require current authority; resource lifecycle, sharing revocation, quotas/provider admission and settlement remain enforced. A permission change does not scan/cancel every open job or create reusable authority for unrelated actions. Session revoke-all/concurrent-login behavior remains separate.

## Accepted session-revocation meaning

**Accepted by the owner:** user/admin selected-session revocation ends the selected application session; revoke-all ends the target account's existing application sessions, including the current one when applicable. A later new Google sign-in is allowed and uses current application permissions. Revocation must not implicitly disable the account or restore removed grants; account suspension remains outside this scope.

Invalidate revoked sessions on the server so an old cookie cannot resume them. The [OWASP session-management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html#session-expiration), checked 2026-11-05, supports server-side invalidation; it does not choose this application's future-login policy. This policy makes no promise to end Google's own session or require Google to prompt for a password. The tradeoff is that session revocation alone cannot keep someone out if they can authenticate again. Exact ordering of concurrent login/revoke-all, and already-admitted work interactions, remain bounded-design inputs; no concurrency protocol or new account-blocking feature is selected here.

## Accepted permission feedback

**Owner decision, 2026-11-06:** hide administrative areas unless the current account has the relevant permissions. Ordinary actions can remain visible but greyed out/disabled, with a short explanation or suitable notification when permission is missing. Exact tooltip, toast, notification-dropdown or inline presentation is a UI design choice; no separate persistent-notification system is selected.

The backend checks current action permission and ownership on every new protected request. An already-open page may have stale controls: if a user submits an action after losing permission, reject it and explain the denial; do not rely on the element having been disabled or accept browser-supplied permissions. Do not retry the rejected action automatically or send a still-authenticated user through Google login merely because permission changed.

New grants take effect through current server checks in the same valid application session. The UI can refresh its displayed permission state without logging out/in; exact refresh triggers/cadence and API shape belong in the bounded design. Immediate push updates or a separate permission-status request before every button are not required by this decision. Normal session expiry/revocation and the pre-write fresh-sign-in rule still apply independently. Preserve K0's non-disclosing ownership denial and same-account draft/privacy boundaries.

## Google configuration and failure handling

**Accepted setup behavior, 2026-11-06:** when `app.auth.enabled=true`, missing/blank required Google configuration stops startup with a clear operator error naming the missing setting without displaying secrets. When false, Google configuration is not required. Never change the configured sign-in mode automatically. The owner first accepted these setup rules, requested provider/framework research, then accepted the recovery policy below on 2026-11-06.

The [Google/Spring failure investigation](../../research/google-sign-in-failure-handling.md), checked 2026-11-06 against Google guidance and the locally managed Spring versions, distinguishes provider behavior, framework defaults and application choices. The intended server integration uses Spring Security OIDC, not a browser Google SDK with an assumed retry policy. No configuration or code is implemented by this research.

**Recovery policy accepted by the owner, 2026-11-06:** end a transiently failed login attempt safely and offer a user-triggered new sign-in with new authorization state/code. Do not automatically replay a callback or code exchange: Google directs obtaining a new code after code-exchange `invalid_grant`, and an ambiguous timeout may follow successful consumption of a one-use code. If the browser never returns from Google's page, the application cannot display its own callback error. Distinguish cancellation/denial, configuration/protocol/identity failures and temporary transport/server failure; unknown failures get a neutral message, not an invented outage diagnosis. Log only safe stage/category/correlation evidence.

Existing application-session continuity is an architecture goal to verify, not an SDK guarantee. Ordinary requests should use local session/current-permission checks without Google calls; other application/database dependencies must remain healthy. Preserve the 30m idle/8h absolute limits and the <=5m pre-write fresh-sign-in rule. Do not invalidate all sessions merely because one attempt fails, extend expired authority or promise every write remains usable during an outage. Failed same-browser reauthentication needs specific verification because Spring clears the current security context on authentication failure. Startup discovery, JWK/decoder caching, UserInfo dependency, explicit transport timeouts/retry behavior and failure-handler presentation are bounded-design choices; the research does not select their final configuration.

[Spring Boot configuration validation](https://docs.spring.io/spring-boot/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.validation), checked 2026-11-05, supports validating bound settings. Exact required keys, conditional binding and sanitized errors belong in the bounded design. Locally present values do not prove that Google accepts credentials/callbacks; real-provider acceptance remains separate. No live sign-in, induced outage or compiled integration/fault test was run.

## Accepted authentication-mode behavior

**Owner decision, 2026-11-06:** keep `app.auth.enabled` as an explicit YAML boolean for development/tests with sign-in both off and on. Common and production-profile defaults remain true; `dev` remains false. Test cases can explicitly select either value. The repository's production Spring profile is named `prod`; the owner's reference to production means that profile, not a hostname, deployment location or frontend build mode. No profile rename is selected.

Changing the boolean must **not invalidate existing Google application sessions**. Their normal inactivity/absolute deadlines, revocations and current-permission checks still apply; changing modes neither resets nor freezes their timers and never revives an expired/revoked session. A still-valid session can resume after sign-in is re-enabled. This supersedes the rejected proposal to invalidate old-mode sessions and force Google login solely because the setting changed. Ordinary restart/session persistence remains required.

When `prod` is active and the effective boolean is false, show administrative users a prominent red application banner: **“Sign-in is disabled in the production profile.”** The condition must come from backend effective configuration; do not infer it from a frontend production build or browser address. Determine administrative access from application permissions, without automatically elevating the fallback account. T3 owns trusted mode/principal metadata; T12 integrates the app-wide banner, using text as well as color. The exact administrative audience/API/UI mapping needs bounded design. Explicit production disablement remains allowed; the banner is visibility, not an authentication control.

**Development account selected by the owner, 2026-11-06:** common `app.auth.enabled` is true; the development YAML overrides it to false. In development with sign-in disabled, create a real development user in the database, give it the application's administrative permissions, and automatically establish that user's identity. Reuse the same account/UUID on later starts so its projects and other data persist. This supersedes the earlier recommendation for a basic-permission fallback user and valid-Google-session-first behavior during disabled development mode. There is no manual login, Google account requirement or application password for this development workflow.

Store the account and its permission assignments in the database and use the ordinary permission/ownership/quota paths. Initial creation provisions admin permissions; ordinary restart reuses the persisted assignments rather than restoring explicitly revoked permissions. Exact identifiers and the create-once/concurrency mechanism belong in the bounded design. This is a development fixture, separate from the one-time command for the initial administrator in normal Google-authenticated operation; it must not consume/reset that bootstrap or silently satisfy production administrator availability.

Enable automatic development-user provisioning/identity only for development with effective auth false; the production profile must never activate it, including mixed `dev`/`prod` activation. With auth explicitly true in development, use normal Google authentication and do not auto-sign in the development user. Tests can exercise both values with explicit database fixtures; their setup does not enable development auto-login in production.

During disabled development mode, the effective actor is the development database user. Preserve previously stored Google sessions separately, without using or overwriting their identity; development activity must not renew those dormant sessions. When Google sign-in is re-enabled, an old Google session may resume only if its normal deadlines/revocation still permit it. Prevent private draft transfer or automatic write replay across the actor change. Exact cookie/security-context representation and cross-instance checks remain design inputs; all serving instances must agree on mode.

Production disablement and its red admin banner remain allowed, without automatic use/provisioning of the development administrator outside development. On 2026-11-07 the owner confirmed **A, existing sessions only**, after clarifying ordinary expiry and the rejection of new writes requiring reauthentication. Valid sessions remain usable under their normal limits. The working Technical Plan therefore uses existing valid Google sessions outside development while blocking new Google entry/callback completion; requests without a valid session cannot access protected resources. Ordinary idle/absolute deadlines, explicit revocation and the pre-write reauthentication rule continue. Re-enabling auth is the operator path for restoring fresh entry; no fallback account is added. Blocked actions are rejected without starting or queuing work; after successful reauthentication the user must explicitly retry. This confirms the mode policy, not the full Technical Plan. A matching sanitized startup warning remains recommended, not selected. No account switcher, runtime toggle UI or content migration is selected.

[Spring Boot profiles](https://docs.spring.io/spring-boot/reference/features/profiles.html) support configuration by active profile, and [Spring Security session persistence](https://docs.spring.io/spring-security/reference/servlet/authentication/persistence.html) associates stored authentication with an HTTP session (checked 2026-11-06). Preserving it across our custom boolean and isolating the fallback identity are application design/test obligations, not framework guarantees. No configuration, principal or banner has been implemented or tested.

## Accepted audit policy

**Owner amendment, 2026-11-06:** both administrator and ordinary-user auditing have independent operator configuration. Administrator auditing defaults true but can be disabled; ordinary-user auditing defaults false but can be enabled. Retention is also independent: **administrators 90 days, ordinary users 30 days** by default. This supersedes the earlier always-on-administrator policy and single 90-day retention setting. Other selected behavior remains: permission-gated read-only inspection, metadata/secret exclusions and transactional administrative-change auditing when enabled.

Planned configuration (not implemented):

| Property | Default |
| --- | --- |
| `app.audit.admins.enabled` | `true` |
| `app.audit.admins.retention` | `90d` |
| `app.audit.users.enabled` | `false` |
| `app.audit.users.retention` | `30d` |

Common configuration supplies these defaults; development, production, `test` and `itest` can override each independently. The former planned `app.audit.retention` key is replaced by the category-specific retention keys; no old runtime binding or compatibility migration exists. These are operator settings, not user opt-outs or new in-app toggles. Turning audit off stops future history capture for that category; it does not immediately erase retained history. Turning it on cannot reconstruct activity that was not captured.

When administrator audit is enabled, record privilege grants/revocations, administrator-driven session revocations and initial normal/development administrator provisioning, plus selected action-catalog events performed by administrators. This includes ordinary project actions by an administrator and the development database admin. These actors follow `admins.enabled`, even when `users.enabled` differs; do not fall through to user auditing if administrator audit is disabled. Ordinary-user catalog events follow `users.enabled`. Classify administrative authority at action admission, before self-revocation can change it, using application permissions rather than only a role label. Preserve that category on the record; retention cleanup must not reclassify old events based on the actor's later permissions. Exact administrative grouping and consumer interfaces need bounded design.

Disabling either audit category does not disable existing minimal authentication/authorization-failure diagnostics, permission/ownership checks or functional business/accounting/bootstrap state. Do not duplicate disabled action history into another logging path as a hidden audit substitute.

Record actor or trusted setup identity, target, action, permission before/after or safe operation/session scope, server UTC time, committed outcome and request/operation correlation. Use safe internal identifiers, not raw cookies/session credentials. Exclude Google codes/tokens, passwords/secrets, PDF/chat bodies and unnecessary profile data. Rejected/failed attempts get bounded sanitized failure evidence in ordinary operational logs; they must not appear as committed changes.

Provide a read-only history list behind an explicit inspection permission. Grant initial inspection permission with normal permission-manager and development-admin provisioning, subject to later authorized changes. Reading history grants no private-project/document/chat access. No in-app edit/delete action for individual records is included. Bounded cleanup applies each record's captured category and its configured retention, independently of whether new capture is enabled. Validate positive retention durations and agree cleanup bounds in the design. Current permissions and bootstrap completion persist independently of history retention; database history alone does not solve old-backup authority recovery (M9).

When administrator auditing is enabled, commit an administrative privilege/session-revocation change and its audit row in the same database transaction; audit-write failure rejects/rolls back that action. With administrator auditing disabled, that audit write is omitted and cannot become a required dependency of the action. Business validation and authorization remain unchanged. Additional business/read-event failure handling must remain explicit in the bounded design; do not silently block every request because optional diagnostic auditing fails.

Named action coverage uses metadata only: project creation/opening/rename/deletion, PDF upload/open/archive/unarchive/retry, chat creation/opening/question submission/deletion/source changes, full-project share/import/revocation and own-session controls are the working catalog. Exclude background polling, typing/scroll notifications and PDF range chunks. Detailed event granularity, operation identity/outcomes and read-event failure handling go to bounded design; feature owners add their actual hooks as slices arrive rather than implementing future features in T3.

Check the actor category and its enable flag before constructing/enriching/writing optional audit events. Do not add a queue/service just to discard disabled events later. Bound record sizes, pagination and cleanup. Verify all four enable-flag combinations, including the development admin, and measure event counts, write volume and latency for representative workloads. The 30/90-day values are selected starting defaults, not traffic estimates, capacity guarantees or external/legal requirements. No large or negligible performance impact is claimed without measurement.

[OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html), checked 2026-11-06, supports administrative/security records, restricted access, credential exclusions and performance/failure testing. It does not prescribe the selected enable flags, retention values or transaction/availability policy. No audit schema, API, binding, cleanup or runtime test has been implemented.
