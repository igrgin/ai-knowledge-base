## Three viable approaches

The judgments in the final column are **project inferences**, not measured implementation cost.

| Approach | Verified mechanisms | T3 effort and tradeoff |
| --- | --- | --- |
| Spring `JdbcClient` / explicit JDBC repositories | Spring supplies statement execution, parameter binding, mapping hooks and exception translation; application code owns SQL. `JdbcClient` is a fluent query/update facade. [Spring JDBC](https://docs.spring.io/spring-framework/reference/data-access/jdbc/core.html) | Least dependency/configuration change; more SQL and row mapping for conventional CRUD. Transactions, grant operations and audit projections stay visible in repository methods. Use templates for operations beyond the facade rather than raw connection boilerplate. |
| Spring Data JDBC aggregates plus explicit SQL | Repositories operate on aggregate roots; referenced children belong to that aggregate and are currently deleted/recreated during aggregate persistence. Custom implementations can replace that behavior. [Aggregate model](https://docs.spring.io/spring-data/relational/reference/jdbc/domain-driven-design.html) | Reduces routine root CRUD mapping without introducing JPA entity-state synchronization. Requires deliberate aggregate boundaries; saving an account with its entire grant collection is an awkward default for independent grants and concurrent administrative edits. Separate grant access and targeted SQL retain much of the explicit work. |
| JPA / Spring Data JPA plus explicit SQL | Derived queries, JPQL and native queries are supported; repository query methods can carry lock metadata. [Queries](https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html), [locking](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html) | Strongest conventional entity/relationship CRUD convenience, with additional mappings and persistence-context rules. Targeted SQL remains useful for bulk grants and cross-account invariants. Correctness is viable, but a mixed implementation must make synchronization and transaction configuration explicit. |

Spring Data JDBC supports declared SQL, pagination and modifying queries; a `Page` can require a count, while a `Slice` fetches enough rows to establish whether more exist. This can simplify ordinary lists without removing query design. [Data JDBC queries](https://docs.spring.io/spring-data/relational/reference/jdbc/query-methods.html)

None of these choices makes a repository `save()` enforce a cross-account security invariant automatically. Neither atomicity nor ownership makes JDBC the only safe option.

## T3 operations that determine fit

The following are implementation implications of the [selected grant model](../designs/t3-identity/design_draft.md#2-permission-storage--selected-per-account-grants), not an approved schema or locking design.

**First Google account creation:** enforce issuer/subject uniqueness in PostgreSQL and atomically create the application UUID, identity link and initial basic grants. An application lookup followed by an unconstrained insert is insufficient under concurrent callbacks. All stacks need the same database uniqueness and a defined conflict/re-read or transaction-retry path. PostgreSQL supports constraint-backed `ON CONFLICT` and `RETURNING`; these are available through explicit SQL in any option. [PostgreSQL INSERT](https://www.postgresql.org/docs/17/sql-insert.html) Email does not merge identities. Returning login and restart preserve grants.

**Individual grants and templates:** conventional account/catalog/template CRUD suits either Data repository style. Actual authority is per-account grant rows: missing means absent, without permanent deny records or account/template membership. Additive template application naturally fits targeted insert/select or batched inserts with grant uniqueness; removal fits a predicate-bound delete. An intentional global grant can restore an earlier removal. It needs explicit target/progress and retry semantics so ordinary recovery cannot replay a completed rollout over a later removal. Template editing alone cannot synchronize accounts. Loading and saving every account/grant graph is unnecessary for these operations, including with JPA.

**Last manager, bootstrap and admission:** a count followed by independent grant removal is unsafe under competing managers. The design must choose shared serialization/locking or another proven database protocol, coordinate every relevant mutation, and atomically order current-grant checks against admitted operations. Normal bootstrap must consume durable completion once while granting its target; development provisioning remains separately create-once. PostgreSQL row locks block conflicting writers until transaction end, and consistent acquisition order matters for deadlocks. [PostgreSQL locking](https://www.postgresql.org/docs/17/explicit-locking.html) JPA lock annotations or explicit JDBC SQL can implement parts of a protocol; neither selects its correct lock scope. Completion evidence must survive audit cleanup.

**Audit:** when administrator capture is enabled, grant/session changes and their audit records must share one committing transaction; failure rolls back both. Disabled capture omits enrichment/write and its dependency. Retention follows the captured actor category, not later grants. Read-only audit inspection should use bounded projections and deterministic ordering; a time-plus-unique-ID keyset is a candidate for sequential browsing, while bounded page/slice queries may suit simpler lists. Exact filters, indexes, cleanup bounds and page/count needs remain unresolved. These are [accepted audit requirements](../designs/t3-identity/authentication-decisions.md#accepted-audit-policy), not evidence of traffic or performance.

## Transactions and mixed access

With JDBC or Data JDBC, retain short service transactions over the same datasource; parameterize UUIDs, keep constraints/locks inside, and release connections before Google/network/filesystem waits. K0 defaults to READ COMMITTED and requires explicit rollback semantics for checked failures. Aggregate repository transactions do not replace a service transaction spanning grants, bootstrap and audit. [K0 conventions](../contracts/k0-foundation.md#jdbc-transactions)

For mixed JPA/JDBC, `JpaTransactionManager` supports one `EntityManagerFactory` and direct JDBC using its same datasource, with an appropriate vendor `JpaDialect`. JDBC must use Spring-aware connection acquisition such as `DataSourceUtils`/templates, rather than acquiring an unrelated connection. The manager must know the matching datasource. Two independent local transaction managers do not become one atomic transaction merely because both use PostgreSQL. [Manager contract](https://docs.spring.io/spring-framework/docs/current/javadoc-api/org/springframework/orm/jpa/JpaTransactionManager.html)

**Mixed-access design obligation:** explicitly flush pending entity changes before JDBC that depends on them; after JDBC/native bulk changes, refresh affected entities or clear/reload before trusting managed state. Clear only after preserving intended pending changes. Spring Data documents that modifying queries can leave outdated entities and does not automatically clear because that could discard unflushed work. [Modifying-query behavior](https://docs.spring.io/spring-data/jpa/reference/jpa/query-methods.html#jpa.modifying-queries) Transaction sharing alone cannot synchronize entity state. If a second-level/query cache is later enabled, its invalidation for direct SQL also needs a provider-specific rule and verification; none is selected here.

## Sessions are a separate persistence choice

Spring Session JDBC stores HTTP sessions in its own tables; choosing it does not require domain JDBC repositories or exclude JPA. Its default JDBC operations use **REQUIRES_NEW**; transaction customization is supported. Consequently, the same datasource alone does **not** make repository session deletion atomic with an outer audit transaction. T3 must choose and test the transaction participation used for audited revocation, including servlet session save ordering and concurrent requests/login. [Session JDBC storage and transactions](https://docs.spring.io/spring-session/reference/configuration/jdbc.html)

Session listing/revocation and current-grant checks remain application requirements alongside custom activity/absolute deadlines and dormant development-mode sessions. Session serialization of authorities cannot replace current database grants. The actual [Hikari configuration](../../backend/src/main/resources/application.yml) is **maximum pool 4**, **connection timeout 2000 ms**, minimum idle zero. Session operations, permission reads and audit writes compete for that pool; nested independent transactions can need another connection while an outer transaction holds one. This is a contention hypothesis requiring measurement, not proof the pool is inadequate or any stack faster.

## Bounded recommendation and remaining validation

**Inference:** retaining `JdbcClient`/explicit repositories is the smallest T3 change and a good fit for its targeted grant mutations and explicit concurrency protocols. Data JDBC is a credible middle option if aggregate CRUD savings justify its boundary work; JPA is credible if entity CRUD productivity justifies mixed-state rules. Future T5/T6 ownership queries, reservations and claims provide consumer context, not permission to design their schemas or force today's stack. No ORM, dependency, module, service or cache is selected by this note; changing the convention requires the owner decision and K0 amendment.

Before implementation, settle exact schema/indexes, manager/connection configuration, lock order, bootstrap/rollout progress, admission ordering, audited session-revocation participation and cache/entity rules if applicable. Verify real PostgreSQL races for duplicate first login, final-manager removal, bootstrap, rollout/removal and session revoke/save/login; rollback on enabled audit failure; disabled audit independence; restart preservation and current-grant visibility. Measure representative query counts, plans, pool wait/timeouts, lock waits, transaction duration, audit volume and memory. No code, dependency installation, benchmark, provider call or remote mutation was performed; there is **no measured performance or scaling winner**.
