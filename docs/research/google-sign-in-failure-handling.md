# Google sign-in failure handling

Checked: **2026-11-06, Europe/Zagreb**. Supporting research for [issue #3 / T3](https://github.com/igrgin/ai-knowledge-base/issues/3), following the [Google investigation](google-sign-in-investigation.md) and [authentication decisions](../designs/t3-identity/authentication-decisions.md). This note supplies evidence for an owner decision; it does not authorize implementation.

## Accepted recovery policy and implementation limits

The owner accepted this configuration-failure policy: with `app.auth.enabled=true`, missing/blank required Google configuration stops startup with a clear operator error naming the missing setting without exposing secrets; with authentication disabled, startup needs no Google configuration. Never switch authentication mode automatically. Present configuration does not prove that Google accepts the credentials, client or callback.

**Recovery policy accepted on 2026-11-06; implementation unverified:** when a Google-dependent sign-in step fails transiently and the application receives control, end that attempt safely and offer a user-triggered **new sign-in**. Do not automatically replay the callback or authorization-code exchange. Keep ordinary requests using an independently valid application session available within existing expiry, revocation and permission limits, provided their application/database dependencies remain healthy. Retain the accepted **30-minute idle / 8-hour absolute** defaults: with **five minutes or less** remaining before the absolute limit, new uploads and other state-changing actions require fresh Google sign-in. An outage cannot extend those limits or bypass that pre-write rule; established-session continuity does not promise those writes remain available. [Accepted timing policy](../designs/t3-identity/authentication-decisions.md#research-and-audit) The details and limits below constrain implementation of this accepted policy.

The intended integration remains server-side Spring Security OIDC with PostgreSQL application sessions. Google's documentation supports server-side code flow and recommends established OAuth libraries; it distinguishes browser JavaScript sign-in libraries from server integrations. No browser Google Identity Services SDK is needed merely to implement the proposed failure handling. Google's generic Java API-client timeout/backoff examples do not configure Spring Security. [Google server integration][google-web], [Google Java timeout guidance][google-timeouts]

## Google/protocol behavior and what the application can observe

| Boundary | Primary evidence | Consequence for the proposed application |
| --- | --- | --- |
| Browser follows the authorization redirect | Google can return errors to the callback or display its own error page. Invalid client/redirect configuration can prevent a safe return. [Google OIDC errors][google-reference] | Once the browser leaves the application, an unreachable Google page, closed tab or Google-hosted error may produce **no callback**. The backend cannot render an error in that absent response or conclusively diagnose a Google-wide outage. Returning to the application's login page can offer a fresh attempt. |
| Consent denied/cancelled with a callback | Google documents `error=access_denied`; its OIDC reference says the user **or authorization server** may deny access. [Google consent response][google-web], [Google OIDC errors][google-reference] | Show a neutral “Sign-in was not completed” result with an optional fresh attempt. Do not assert that the user cancelled, or classify every denial as a temporary outage. Closing the browser may have no callback. |
| Transient authorization error returned to callback | OAuth defines `server_error` and `temporarily_unavailable` for authorization responses. Google's inspected OIDC table does not enumerate these two codes. [RFC 6749 §4.1.2.1][oauth-errors], [Google OIDC reference][google-reference] | Support safe handling if received; do not claim Google guarantees either code for every outage. No authentication or automatic redirect loop should result. |
| Token exchange fails | Google defines `invalid_client` as failed client authentication; `invalid_grant` includes invalid/expired/revoked codes or redirect mismatch. Its code-exchange guide directs the client to obtain a new code after `invalid_grant`. [Google token errors][google-reference], [Google code-exchange guidance][google-web] | Configuration/protocol errors need operator diagnosis, not a “Google temporarily unavailable” diagnosis. Transport failure, timeout or HTTP 5xx can justify a retry-later message, but do not prove a global provider incident. |
| Token exchange response is lost | Authorization codes are single use. The OAuth standard forbids reusing a code; duplicate use must be rejected and previously issued tokens should be revoked where possible. [RFC 6749 §4.1.2][oauth-code] | A timeout or connection loss does not establish whether Google already consumed the code. Restarting authorization is the conservative application recovery; blindly retrying the token POST is unsafe. |

Google's [Java HTTP-client backoff guide][google-backoff] describes opt-in exponential backoff for transient HTTP responses and says it is off by default in that library's `HttpRequest`. This is **not** a promise that Google's code-token endpoint is idempotent, nor a default of Spring's client. No inspected Google source established a safe authorization-code replay exception for an ambiguous timeout/5xx. Accepted recovery policy: no automatic application-level token-exchange retry, including after a 5xx; a deliberate new authorization journey uses fresh state/nonce/PKCE material and a new code. Even a failure after successful token exchange, such as missing keys or failed UserInfo, should not cause the code to be exchanged again.

## Spring defaults and additional dependencies

**Callback and failure presentation.** Security 7.1.2's `OAuth2LoginAuthenticationFilter` removes the matching stored authorization request before invoking authentication; a replay normally lacks that request. `HttpSessionOAuth2AuthorizationRequestRepository` checks callback state when loading it. The OIDC provider rejects error responses and validates the login/token path. [Callback filter][spring-filter], [request repository][spring-request], [OIDC provider][spring-provider]

The ordinary `oauth2Login()` configurer inherits the failure redirect to **`/login?error`** (or a configured login page plus `?error`). `SimpleUrlAuthenticationFailureHandler` stores the exception and redirects; a standalone handler without a failure URL instead returns 401. This is not an application-specific, classified retry UI. Errors while constructing/sending the initial authorization redirect have a separate filter handler whose default sends **500**. Neither handler can intercept a browser failing to reach Google after a successful redirect. [Configurer default][spring-configurer], [failure handler][spring-failure], [authorization redirect filter][spring-redirect]

**Token HTTP client.** With no replacement bean/configuration, `OAuth2LoginConfigurer` selects `RestClientAuthorizationCodeTokenResponseClient`. Its base class performs one POST/retrieve/body path, with no explicit retry/backoff loop or explicit timeout settings. `RestClientException` becomes `invalid_token_response`; structured OAuth errors take a different path, and HTTP status/cause matter for classification. In particular, `OAuth2ErrorResponseErrorHandler` delegates non-400 errors to the normal error handler, so do not assume every Google 401 preserves `invalid_client` as the top-level OAuth code. [Client selection][spring-login], [token implementation][spring-token], [error handler][spring-error]

Framework 7.0.10's raw `RestClient` builder selects the request factory from the available classpath: Apache, Jetty, Reactor Netty, JDK, then the simple factory. Its JDK factory creates a default JDK HTTP client and leaves the request timeout unset unless configured. Thus **there is no verified universal token timeout or transport retry count** here, and Boot's application HTTP-client settings must not be presumed to customize this privately constructed client. Select and wire the transport deliberately, bound connect/read/overall work appropriately, and verify that its automatic behavior cannot replay the code POST. Underlying network/JDK/client retries were not exhaustively audited. [Framework builder][framework-builder], [JDK factory][framework-jdk], [token implementation][spring-token]

**Discovery.** Google recommends retrieving endpoint metadata from its fixed discovery URI and respecting HTTP caching directives. The [live public discovery document][google-discovery] was readable during this research; this proves neither login nor outage behavior. Boot 4.1.2's properties mapper invokes `ClientRegistrations.fromIssuerLocation` when an issuer URI is supplied; that method performs network discovery while constructing registration, with 30-second connect/read settings. A failure can therefore stop startup, independently of the accepted missing-local-configuration rule. Spring's built-in Google registration contains explicit endpoints and does not need discovery to build it; these are not all the same URLs as current Google discovery. Choose this boundary explicitly in T3: don't promise startup during an outage while selecting uncached startup discovery, or silently substitute endpoint strategies. [Google discovery guidance][google-guide], [Boot mapper][boot-mapper], [registration discovery][spring-registration], [Google defaults][spring-google]

**Signing keys.** Google recommends cached public keys and local signature validation, with HTTP cache directives respected; `tokeninfo` is a debugging facility that can itself fail or be throttled. A cold cache, unknown signing key or required refresh can make key availability a login dependency; inability to validate must fail authentication. [Google token verification][google-guide]

Version-specific caveat: the inspected OIDC provider calls `jwtDecoderFactory.createDecoder` for each ID token, and the default `OidcIdTokenDecoderFactory` builds a **new** Nimbus decoder in that method. Do not assume that the decoder's ordinary in-memory JWK cache survives separate sign-ins. Within a reused decoder, Security's default Nimbus construction enables caching and disables refresh-ahead/rate-limiting; the inspected Nimbus 10.9.1 source defaults its cache TTL to five minutes and leaves retry/outage-tolerant wrappers disabled. Spring's JWK fetch path does not implement Google's HTTP cache-directive policy. None of this proves offline new-login availability. A deliberate reusable decoder/cache and its refresh/failure behavior require design and tests. [OIDC provider][spring-provider], [decoder factory][spring-decoder], [Nimbus integration][spring-nimbus], [Nimbus 10.9.1 source artifact][nimbus-source]

Spring's JWK HTTP client differs from its token client: `NimbusJwtDecoder` installs connect/read timeouts from a helper, defaulting each to **30 seconds**, with the corresponding JDK system-property overrides. These are source defaults for that path, not measured end-to-end sign-in latency or a selected application budget. [Nimbus client][spring-nimbus], [timeout helper][spring-jwt-timeouts]

**UserInfo.** Security 7.1.2's default OIDC user service retrieves UserInfo whenever its endpoint is present and the grant is authorization code, including an `openid email` login; this is not avoided merely by omitting `profile`. It checks that UserInfo `sub` matches the ID token, and retrieval failure aborts login rather than quietly falling back. The delegated service creates a raw `RestTemplate`; its simple factory leaves timeouts to system defaults. Recommendation for bounded design: decide whether verified ID-token claims meet the identity/profile requirements and deliberately omit UserInfo, or retain it as a required, bounded login dependency. Do not silently accept unvalidated data or fallback after a validation failure. [UserInfo predicate][spring-user-predicate], [OIDC user service][spring-user], [delegated HTTP service][spring-user-http], [default request factory][framework-accessor], [simple HTTP factory][framework-simple]

## Established sessions and recovery implementation

Spring Session's servlet filter loads sessions through the repository; JDBC session lookup reads the database and rejects expired sessions. Spring Security can load the stored security context from `HttpSession`. **Inference for the proposed architecture:** ordinary application requests need not contact Google once a valid application session exists. This depends on the actual filter chain and application avoiding provider refresh, UserInfo, introspection or revalidation on those requests. Database/app failure, expired/revoked sessions, changed permissions and mandatory fresh sign-in remain independent constraints. Login alone does not implement immediate Google-side revocation propagation. [Session 4.1.1 filter][session-filter], [JDBC repository][session-jdbc], [security context][spring-context]

Implementation guidance for the accepted recovery policy; exact dependency, handler and transport choices remain bounded-design inputs:

- When control returns after a transient sign-in failure, show a stable local message such as “We couldn't complete Google sign-in. Please try again later,” and a fresh sign-in action. Preserve intended safe return location and unsent work under existing account/privacy rules; never preserve authenticated authority from an incomplete attempt.
- Distinguish denial, expired/missing login transaction, operator configuration errors and unverifiable identity from transient transport/server failures. Unknown failures get a neutral failure message. Never render raw provider `error_description`, exception text, codes/tokens or callback URLs containing credentials.
- Log a sanitized category, failed stage, HTTP status when available and correlation identifier for operators; exclude client secrets, code/state/nonce, tokens and private profile data. Broad codes such as `invalid_token_response` or `invalid_id_token` alone cannot reliably distinguish configuration, malformed responses and transport/JWK failure.
- Do not invalidate every application session solely because one Google attempt fails. Preserve the accepted idle/absolute limits, revocation checks and pre-write reauthentication boundary; an outage cannot renew expired authority. Failed same-browser reauthentication needs explicit testing: Spring's unsuccessful-authentication path clears the current security context, so session behavior must not be assumed from the generic policy. [Failure processing][spring-processing]
- Do not require Google availability in ordinary application liveness or add a Google preflight call to every request. Explicitly resolve startup discovery and selected login dependencies before promising degraded operation.

## Verification still required

No implementation, credentials, Google-console inspection, live sign-in, induced outage, compiled integration or fault test was performed. Public documentation/source retrieval is the only external operation. No latency, provider uptime, retry count for the final transport, cache survival or successful session continuity was measured.

The bounded T3 design should name the chosen registration/discovery strategy, decoder/cache lifetime, UserInfo choice, explicit HTTP transport/budgets and safe failure-handler contract. Its checks should cover missing-config enabled startup and disabled startup without Google settings; browser no-return versus callback denial/error; token timeout/5xx and ambiguous consumed-code response loss; callback replay; malformed/invalid token versus unavailable keys; cold/warm/rotated-key cases; UserInfo failure when enabled; existing valid sessions and mandatory reauthentication during outage; and sanitized diagnostics. Verify cancellation and actual provider configuration separately with real Google. Controlled offline tests cannot establish Google's live outage responses. No numeric application timeout or retry schedule is selected by this research.
