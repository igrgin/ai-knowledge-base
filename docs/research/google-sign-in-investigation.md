# Google sign-in investigation

Checked: **2026-11-05, Europe/Zagreb**. Repository baseline: `e095a9161f3382aa9ee1a83db6198f3f93f94f76`, branch `egm-foundation-bootstrap`. Existing untracked `langchain-architecture-assessment.md` was left untouched. This is supporting research for [issue #3](https://github.com/igrgin/ai-knowledge-base/issues/3), requested before resuming its EGM brainstorm; it is not an implementation handoff or a Goldfish review. Google account/project configuration, client credentials, domain ownership and actual sign-in have **not** been inspected or verified.

## Authority and conclusion

The owner selected **Google as the sole login provider** and clarified that local startup means running the backend from IntelliJ with supporting services for development. The latest decision controls sign-in through application YAML: **off by default in `dev`, on by default in `prod`, with explicit overrides allowed**. This supersedes the hard development-only restriction in commit `4f9a737` and the broader local-product interpretation in `da08ee3`. No application password login or administrator portal is requested.

These decisions supersede the older email/password proposals in the [application design](../designs/application.md), including R1, C7, D-A, the authentication API/data inventory and T3 description, and the password wording in the [roadmap](../roadmap.md). The integrator records the accepted scope there; this note supplies evidence and leaves implementation recommendations open for design. Public self-registration without invitation, private ownership and persistent sessions remain product requirements. The developer shortcut must exercise the same application-account ownership paths without needing Google login.

Recommendation for the signed-in mode: use Spring Security's server-side OIDC authorization-code login and Spring Session JDBC. This fits the existing same-origin Spring MVC application and shared PostgreSQL direction without a runtime upgrade. Keep the application's UUID account identity separate from Google identity and keep Google tokens out of browser storage. Google documents a backend server flow; Spring documents Google OAuth2 Login establishing an authenticated session. [Google server flow](https://developers.google.com/identity/openid-connect/openid-connect#server-flow), [Spring Google login](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/core.html)

This recommendation does **not** settle invitation semantics, session duration, relinking or immediate response to provider-side revocation. Those decisions are listed below.

For the developer launch, recommendation: an explicit YAML authentication setting supplies a server-established development account/principal. Keep normal ownership predicates, account quotas and feature behavior. Authentication-enabled configurations must reject bypass access; missing Google configuration must not enable it. The default loopback startup remains suitable for the stated IntelliJ workflow; no LAN-use product or local-to-Google migration is requested. The exact fixture, profile/run configuration and safeguards need T3 design. A controlled OIDC issuer used in automated tests is a separate tool and does not satisfy this developer convenience by itself. [K0 trusted identity](../contracts/k0-foundation.md#identifiers-and-trusted-identity), [current local startup](../local-development.md)

Accepted configuration detail: the planned property is `app.auth.enabled`, with common default true, `dev` false and `prod` true. Explicit overrides are allowed. Tests must cover the defaults and overrides, Google-disabled startup without credentials, and absence of automatic fallback when credentials are missing with sign-in enabled.

## Existing-version fit

The [root POM](../../pom.xml) pins Boot **4.1.2** and Java **26**; [backend/pom.xml](../../backend/pom.xml) already uses MVC, JDBC, PostgreSQL and Flyway but has no security/session dependency. The locally cached Boot 4.1.2 BOM resolves Spring Security **7.1.2** and Spring Session **4.1.1**, matching the inspected official documentation. Boot's published coordinates manage those versions and the `spring-boot-starter-security-oauth2-client`, `spring-boot-starter-session-jdbc` and corresponding test starters. Use managed versions rather than independently pinning or upgrading these libraries. [Boot 4.1.2 managed dependencies](https://docs.spring.io/spring-boot/appendix/dependency-versions/coordinates.html)

Boot supplies servlet JDBC-session auto-configuration through its session JDBC starter. Spring Session stores sessions and attributes in PostgreSQL-compatible tables; its JDBC reference supplies vendor-specific schema scripts. Recommendation: adapt the **4.1.1** PostgreSQL schema into an integrator-numbered additive Flyway migration and disable competing session schema initialization. Preserve V1 and K0's sole-Flyway ownership. JDBC sessions do not decide the separate open JDBC/JPA choice for domain persistence. [Boot session configuration](https://docs.spring.io/spring-boot/reference/web/spring-session.html), [Session JDBC schema](https://docs.spring.io/spring-session/reference/configuration/jdbc.html#jdbc-schema), [K0 migration rules](../contracts/k0-foundation.md#migrations-and-integration-fixtures)

No dependency was added, no application was compiled for this investigation and no real session compatibility is claimed yet.

## Google setup and callback addresses

The person operating the Google project must create/select a Cloud project, configure its Google Auth Platform branding/audience/data access, and create a **Web application** OAuth client. A server client uses a client ID and secret; keep the secret in server configuration outside committed source and browser assets. This is Google project setup, not an application administrator feature. [Google setup](https://developers.google.com/identity/openid-connect/openid-connect#settingup), [OAuth client creation and secret handling](https://support.google.com/cloud/answer/15549257)

Use an External audience for the existing public-registration requirement. Internal audience is limited to a project's Google organization; External does not guarantee that every Workspace or protected account can authorize the app. Google policy requires separate testing and production projects. [Audience and account restrictions](https://support.google.com/cloud/answer/15549945), [OAuth environment separation](https://developers.google.com/identity/protocols/oauth2/policies#separate-projects)

Spring's default callback is `{baseUrl}/login/oauth2/code/{registrationId}`. For registration `google`, the following are candidate registrations, **not configured or selected deployment URLs**. Google requires the request URI to match its registered URI; HTTPS is required except for localhost, including loopback IPs. No wildcard callback is available. [Spring callback template](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/core.html#oauth2login-boot-redirect-uri), [Google URI rules](https://support.google.com/cloud/answer/15549257#authorized-redirect-uris)

| Environment | Candidate authorized redirect URI | Repository implication |
| --- | --- | --- |
| Packaged/default local backend | `http://127.0.0.1:8080/login/oauth2/code/google` | Matches current loopback host/port. |
| Localhost alternative | `http://localhost:8080/login/oauth2/code/google` | Separate exact URI; choose one host consistently for the browser journey. |
| Custom local backend port | `http://127.0.0.1:18081/login/oauth2/code/google` | Register the actual selected port; existing docs demonstrate 18081. |
| Vite browser origin, if auth is proxied | `http://127.0.0.1:5173/login/oauth2/code/google` | Requires T3 proxy/base-URL/cookie handling; it is not supported by today's readiness-only proxy. |
| Future hosted environment | `https://<actual-app-host>/login/oauth2/code/google` | Replace the placeholder only after a host is selected; configure trusted proxy handling if applicable. |

The [current Vite config](../../frontend/vite.config.ts) proxies only `/actuator`; [local development](../local-development.md) distinguishes frontend 5173 from backend 8080. Recommendation: design one browser-facing auth origin for development, proxy its API/login/callback/logout paths as needed and test the complete round trip. Otherwise, explicitly design the transition to/from the backend origin. Do not assume a backend callback plus a redirect to Vite already works. Registering JavaScript origins is relevant to browser Google API clients; the proposed server redirect flow does not require adding a browser token SDK. [Google client types/origins](https://support.google.com/cloud/answer/15549257#web-applications)

Spring's Google defaults include known endpoints and issuer `https://accounts.google.com`; Google discovery currently advertises newer token/userinfo URLs than some Spring defaults. Both are first-party configurations; do not silently replace them or assume a defect. Choose documented defaults versus discovery in T3 and prove the chosen path. Discovery-based registration can perform network requests when constructed. [Security 7.1.2 Google defaults](https://raw.githubusercontent.com/spring-projects/spring-security/7.1.2/config/src/main/java/org/springframework/security/config/oauth2/client/CommonOAuth2Provider.java), [Google live discovery](https://accounts.google.com/.well-known/openid-configuration), [Spring registration discovery](https://docs.spring.io/spring-security/reference/servlet/oauth2/client/core.html#oauth2Client-client-registration)

## Scopes, publishing, verification and costs

Recommendation: explicitly request `openid email`; include `profile` only if name/avatar improve the chosen UI. `email` supplies email and verification claims; profile claims are optional, so missing names/pictures must not break login. Do not request Drive/Gmail/Calendar scopes, `access_type=offline`, or a refresh-token store for this identity-only use. Google's reference distinguishes online from offline access; application session persistence is a separate concern. [Google OIDC reference](https://developers.google.com/identity/openid-connect/reference)

Google's Testing status normally limits access to listed test users (up to 100) and expires authorization after seven days. **The same official page explicitly exempts requests limited to `openid`, email and profile:** users need not be listed, do not receive that testing warning and their authorizations do not expire after seven days. Adding another scope changes this analysis. This exception says nothing about the application's session timeout. Production publication makes the app available to Google accounts subject to applicable verification/account restrictions. [Exact Testing exception and production status](https://support.google.com/cloud/answer/15549945#publishing-status)

Do not claim either “every Google login app must pass sensitive-scope verification” or “production needs no verification.” Brand verification has separate conditions for an External, published app displaying a name/logo, and domain ownership/policy/homepage requirements apply when preparing that process. Development/testing/staging apps have verification exceptions. Recheck the actual console status and requested scope set before release; no verified branding or approval is established here. [Brand verification criteria and preparation](https://developers.google.com/identity/protocols/oauth2/production-readiness/brand-verification), [Verification exceptions](https://support.google.com/cloud/answer/13464323?hl=en)

The inspected primary sources did not establish a direct-OIDC tariff or a verification-charge amount. This note therefore makes **no numerical fee, universal “free” claim or mandatory security-assessment fee claim**. It does not select Firebase Authentication or paid Identity Platform. Any later service/resource purchase needs its own current evidence and authority.

## Identity, changed email and invitations

Google states that `sub` is unique, never reused and unchanged even when an account's email changes. OIDC defines issuer plus subject as the stable identity pair; email/name are not stable account keys. [Google subject stability](https://developers.google.com/identity/openid-connect/openid-connect#obtainuserinfo), [OIDC claim stability](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)

Recommendation: persist the verified Google issuer/subject with a unique constraint mapping to the existing K0-style server-generated application account UUID. Resolve ownership through that UUID. Treat email as profile/contact data, not a user-selected login key or a uniqueness rule that merges accounts. Use an explicit trusted issuer configuration; do not accept arbitrary issuer URLs or transform unvalidated claims into trusted identity. T3 must decide its canonical representation for Google's documented issuer forms while retaining framework validation. [Google issuer forms](https://developers.google.com/identity/openid-connect/openid-connect#obtainuserinfo), [K0 identity](../contracts/k0-foundation.md#identifiers-and-trusted-identity)

Google's email assurance differs by account type: it is authoritative for Gmail, and for Workspace when `email_verified=true` and `hd` is present. For a Google account using an external mailbox, `email_verified=true` can reflect verification at creation even though that mailbox's owner later changed. Use the validated `hd` claim for a Workspace restriction, never an email suffix or an authorization-request hint. [Google email authority caveat](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)

**Consequence for T16/T17:** Google authentication proves the Google account identity; it does not universally prove present control of every claimed external mailbox. A named invitation/restricted snapshot cannot safely bind an existing account merely because its current email text matches. An address change must not transfer existing projects or grants. These are design implications of the cited assurance limits, not newly accepted sharing rules. The development shortcut does not create a new product sharing mode.

Options to resolve in design include selecting an already-registered recipient by application identity, or explicitly designing an email-address claim/acceptance procedure with adequate current-mailbox proof. The latter could introduce the email dependency currently deferred by C7; no such service is authorized here. Preserve the distinction between named invitations and registered-link acceptance. Do not silently restrict all login to Gmail/Workspace, remove named invitations, equate a named invitation with link possession, or introduce account enumeration through recipient search. [Existing R26/R27 and D-K/D-L](../designs/application.md#d-k-independent-project-imports)

Recommended lifecycle boundaries for review:

- A returning issuer/subject resolves the same UUID after an email change; refresh display/contact data only through a deliberate policy. Test collision with another account's email.
- A new subject must not automatically link/merge into a prior UUID because emails match. Lost Google access does not establish a new account's right to old private content.
- Owner decision: the first successful Google sign-in creates the application account automatically with no further onboarding and immediate ability to create projects. Implement atomic issuer/subject uniqueness; consent denial or failed validation must not provision a usable account.
- No account relinking, recovery operator or administrator portal is added by the provider choice. If later required, define proof, audit and existing-session/grant behavior separately. Google itself leaves new-user onboarding/auto-registration to the application. [Google application-account step](https://developers.google.com/identity/openid-connect/openid-connect#authenticatingtheuser)

## Security and persistent sessions

Keep Spring's code exchange and validation path. Security 7.1.2 checks stored request state, requires an ID token and validates the request nonce when present; its ID-token validator checks required claims, issuer, audience/authorized party and timestamps. Retain signature verification with trusted Google keys. Test nonce generation and validation through the selected configuration instead of adding hand-decoded JWT acceptance. [Code-flow provider source](https://raw.githubusercontent.com/spring-projects/spring-security/7.1.2/oauth2/oauth2-client/src/main/java/org/springframework/security/oauth2/client/oidc/authentication/OidcAuthorizationCodeAuthenticationProvider.java), [ID-token validator source](https://raw.githubusercontent.com/spring-projects/spring-security/7.1.2/oauth2/oauth2-client/src/main/java/org/springframework/security/oauth2/client/oidc/authentication/OidcIdTokenValidator.java), [Google validation requirements](https://developers.google.com/identity/gsi/web/guides/verify-google-id-token)

Security 7.1.2 defaults authorization-code clients to PKCE; Google's discovery advertises S256 support. Preserve and test that protection. Its session authorization-request repository stores the pending request in `HttpSession` and removes it on retrieval for completion, so callback handling on another web instance also needs shared pre-login session state. [Client settings](https://docs.spring.io/spring-security/reference/servlet/oauth2/client/core.html), [Google discovery](https://accounts.google.com/.well-known/openid-configuration), [Session authorization-request source](https://raw.githubusercontent.com/spring-projects/spring-security/7.1.2/oauth2/oauth2-client/src/main/java/org/springframework/security/oauth2/client/web/HttpSessionOAuth2AuthorizationRequestRepository.java)

OAuth state protects the login round trip; it does not replace CSRF protection on application writes/logout. Spring protects unsafe methods by default and provides SPA handling, including fresh-token handling after login/logout. Recommendation: retain CSRF, design a narrow React token-acquisition/header contract, keep the session cookie HttpOnly, use Secure cookies for non-local HTTPS and explicitly permit only the intended loopback HTTP development exception. Review SameSite against the selected redirect mode; do not assume a Strict cookie survives a cross-site callback. [Spring CSRF and SPA guidance](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html), [Session cookie configuration](https://docs.spring.io/spring-session/reference/configuration/common.html)

Spring's session persistence uses the security context; login session-fixation protection changes the session identifier. Recommendation: use a small serializable application principal carrying the UUID, and verify the final context is saved and reloaded correctly through JDBC. Avoid a custom success handler that updates only thread-local authentication. Session attributes, principal compatibility and any saved OAuth state must survive the intended restart/instance boundary. [Security persistence and fixation](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html), [Session HttpSession integration](https://docs.spring.io/spring-session/reference/http-session.html)

OAuth authorized-client storage is **different** from session storage: Spring's default authorized-client service is in memory and a separate JDBC variant stores access/refresh tokens. Recommendation: no durable Google-token table or background refresh for login alone; explicitly review/remove unneeded authorized-client retention and avoid retaining a full token-bearing OIDC principal just to identify the actor. This requires a tested integration choice, not an assumption that `oauth2Login()` stores no tokens. [Authorized-client storage](https://docs.spring.io/spring-security/reference/servlet/oauth2/client/core.html#oauth2Client-authorized-client)

Choose session idle timeout, any absolute lifetime, browser-close persistence, concurrent-session policy and reauthentication points in T3. Boot exposes `spring.session.timeout`; a JDBC row surviving backend restart does not guarantee a browser still has a usable cookie or that the session has not expired. No duration is selected by this note. Test logout against concurrent in-flight requests and later reload through the second instance; do not claim the database store alone proves invalidation races. [Boot timeout](https://docs.spring.io/spring-boot/reference/web/spring-session.html), [Cluster session integration](https://docs.spring.io/spring-session/reference/http-session.html)

Recommendation: local application logout through a CSRF-protected POST, invalidating the session/context and clearing the application cookie. Spring provides that cleanup. It must work without reaching Google and must not automatically start a new Google login on its success page. [Spring logout cleanup](https://docs.spring.io/spring-security/reference/servlet/authentication/logout.html)

Local logout does not sign the user out of Google. Spring's provider logout requires provider support and an `end_session_endpoint`; Google's inspected discovery publishes no such endpoint. Therefore do not promise global Google logout or use an undocumented Google logout URL. Google grant revocation is a separate action from application logout. [OIDC logout distinction](https://docs.spring.io/spring-security/reference/servlet/oauth2/login/logout.html), [Google discovery](https://accounts.google.com/.well-known/openid-configuration), [Google grant revocation](https://developers.google.com/identity/protocols/oauth2/web-server#tokenrevoke)

An established application session in Google sign-in mode is separate from later Google consent/account state. Immediate invalidation after remote revocation/disable is not demonstrated by login alone. Google offers separately integrated signed Cross-Account Protection events; do not assume this exists or silently add it to T3. Decide the accepted lag/revalidation behavior, local account disabling and session invalidation policy, including what happens when Google is unreachable. [Google security-event integration](https://developers.google.com/identity/protocols/risc), [Session persistence model](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html)

## Failures and verification proposal

The following are proposed checks for the later T3 handoff, not tests executed in this research:

| Boundary | Meaningful evidence |
| --- | --- |
| Google-linked identity/PostgreSQL | First-login races produce one issuer/subject mapping; repeat login and changed email preserve UUID; same email/different subject does not merge; failed login creates no usable session; actual account/session migrations persist across restart. |
| Full protocol with a test-only issuer | Real security filters, code exchange and signed test keys; reject bad/missing/replayed state/nonce, invalid signature, wrong issuer/audience/authorized party, expired token, denied consent and broken token/userinfo/JWK responses. Exercise PKCE and safe bounded failures. |
| Browser session | Login-ID rotation, `/me`, CSRF rejection/refresh, expiry, logout/cookie deletion, safe return destinations, reload/deep links, dev proxy and packaged same-origin behavior. An unauthenticated API gets the selected safe JSON response rather than a provider HTML redirect loop. |
| Two web instances | Login starts on A/callback completes on B; authenticated access alternates; restart one/both; logout on B rejects the cookie on A, including the selected concurrent-request behavior. Include database outage and expired-session cleanup. |
| Runtime configuration | In normal Google login configuration, decide and test startup failure versus explicit unavailable-login state for missing/blank credentials. Never silently fall back to development access, passwords, a fixed actor or permit-all routes. In explicitly selected local development, prove IntelliJ/service startup without Google credentials, stable development ownership fixtures, and rejection of bypass access when sign-in is enabled. |
| Named recipient cases | Once the invitation contract is chosen, test non-Gmail external accounts, false/missing verification data, address changes/reuse and distinct Google subjects, plus named versus registered-link access. |
| Real Google acceptance | Separately record a real configured client, exact redirect origin, actual requested scopes, successful first/returning login with two accounts, cancellation, UUID continuity, logout and restart. Do not commit tokens/secrets or claim mock-provider success verifies consent configuration. |

MockMvc `oidcLogin()` constructs an authenticated test user; it is useful for controller/authorization tests but bypasses the protocol exchange and cannot prove token validation, Google configuration or JDBC restart behavior. Use a test-only local issuer for protocol/browser integration, confined to test sources/profiles and absent from normal application success paths. This issuer is separate from the developer launch shortcut and is not another application login provider. [Spring OIDC test support](https://docs.spring.io/spring-security/reference/servlet/test/mockmvc/oauth2.html), [K0 fixtures](../contracts/k0-foundation.md#migrations-and-integration-fixtures)

Native `test`/`itest` and CI should remain independent of Google credentials/network. The developer launch must also work without obtaining a Google session. With sign-in enabled, Google authentication is required: an already valid persistent application session differs from acquiring a new session through Google, which needs provider connectivity. Decide whether real Google acceptance is required for T3 completion or recorded as an outstanding readiness gate; the developer shortcut or mock-provider success cannot establish Google readiness. Existing commands and PostgreSQL conventions remain in [local development](../local-development.md#native-tests).
