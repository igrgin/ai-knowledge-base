## Demonstrable behavior

Register/log in through Google, log out and retain an application session after restart; allow developer startup from IntelliJ without sign-in.

## Owner-selected authentication scope

On 2026-11-05 the owner selected Google as the sole application login provider. The latest clarification defines skipping sign-in as a developer pressing Run in IntelliJ and starting supporting services locally. This is an explicit configured sign-in bypass, not an unauthenticated local-use product. No application password login is included; the later owner request adds administrator session revocation with assignment/permissions still unresolved. Research and EGM brainstorming are authorized; implementation is pending the accepted bounded design, completed review and separate implementation authority.

Resolve the server-established development principal/fixture and configuration behavior in T3. Preserve ordinary account ownership paths and require Google when the setting is enabled. Implement automatic account creation on the first successful Google sign-in, with no further onboarding and immediate project access. Resolve atomic creation/returning lookup, stable provider-to-application identity mapping, administrator session-management permissions, callback/development origin, CSRF/logout/error interfaces and real Google acceptance. No separate local-user edition, account switcher, LAN sharing policy or local-to-Google migration is requested.

Accepted YAML control: `app.auth.enabled` defaults to false in `dev` and true in `prod`, with explicit overrides allowed. Check both values under each profile; missing Google credentials never change the configured value. No-sign-in access uses a server-established account and retains ownership/quota rules. This setting is planned, not implemented.

Accepted session policy: 30 minutes idle and 8 hours maximum from sign-in, both YAML-configurable and server-enforced. Browser reopening and backend restart preserve valid sessions within both limits without resetting session age. Verify each boundary and restart behavior with the real session store. Define the cookie/UI contract for preserving the current view and unsent question on expiry; restore private state only for the same account. T12 and feature owners implement those UI obligations as their features arrive; T3 does not create chat/project UI early.

Owner session-management amendment: each signed-in session has independent inactivity/maximum timers. Add settings/profile controls to revoke one or all of the user's sessions; ordinary sign-out affects the current session, and explicit all-session revocation includes it. Administrators can revoke selected/all sessions of a user under an explicit permission. Admin assignment, exact UI boundary, session/device representation and cross-instance revocation races remain T3 design questions; no broader private-content access or separate admin password login is included.
